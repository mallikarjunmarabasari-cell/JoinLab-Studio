
# JoinLab Studio — v0.3 Architecture

**Milestone:** Accounts and Cloud Persistence
**Status:** Finalized for implementation
**Backend Framework:** Python FastAPI

## 1. Architecture Goals

The v0.3 architecture must support:

1. User registration and authentication.
2. Multiple workspaces per user.
3. Multiple projects per workspace.
4. An independent PostgreSQL database for every project.
5. Persistent local database storage through IndexedDB.
6. Cloud database snapshots through Supabase Storage.
7. Database recovery through snapshot restoration.
8. Secure ownership and access control using Supabase RLS.
9. Python backend development using FastAPI.

## 3. Architecture Responsibilities

### 3.1 React Frontend

Responsible for:
- User interface and navigation.
- Authentication screens.
- Workspace and project management interface.
- SQL editor and Database Explorer.
- Local PGlite initialization.
- Local SQL execution.
- Database snapshot export and restore coordination.

### 3.2 Python FastAPI Backend

Responsible for:
- Authentication token verification.
- Workspace and project APIs.
- Application business logic.
- Project ownership verification.
- Snapshot upload and download operations.
- Snapshot metadata management.
- API validation and error handling.

FastAPI must not execute arbitrary learner SQL against the Supabase application database.

### 3.3 Supabase

Supabase Auth:
- User registration and login.
- Authentication sessions and access tokens.

Supabase PostgreSQL:
- User profiles.
- Workspace records.
- Project records.
- Snapshot metadata.

Supabase Storage:
- Private database snapshot files.

Supabase RLS:
- Enforce user-level data ownership.
- Prevent unauthorized access to workspaces, projects and snapshots.

### 3.4 PGlite and IndexedDB

- PGlite executes learner SQL locally.
- IndexedDB stores the local working database.
- Each project has a unique database storage identity.
- Local SQL execution must not depend on an active internet connection after initialization.

## 4. Entity Relationships

User
  └── Workspace
        └── Project
              └── Independent PGlite Database
                    └── Database Snapshots

Relationship rules:

- One user has one profile.
- One user can own multiple workspaces.
- One workspace belongs to exactly one user.
- One workspace can contain multiple projects.
- One project belongs to exactly one workspace.
- One project has exactly one logical PGlite database.
- One project can have multiple database snapshots.

## 5. Application Database Design

The initial application schema contains four tables:

### profiles
- id
- display_name
- avatar_url
- created_at

The profile ID references Supabase Auth user ID.

### workspaces
- id
- owner_id
- name
- created_at
- updated_at

Each workspace belongs to one user.

### projects
- id
- workspace_id
- name
- description
- created_at
- updated_at

Each project belongs to one workspace.

### project_database_snapshots
- id
- project_id
- version
- storage_path
- created_by
- file_size_bytes
- checksum
- status
- created_at

Each snapshot belongs to one project.

All application tables must use appropriate primary keys, foreign keys, indexes and RLS policies.

## 6. Project Database Lifecycle

### 6.1 Project Creation

1. User creates a project.
2. FastAPI verifies the authenticated user.
3. FastAPI creates the project record in Supabase.
4. The project receives a unique UUID.
5. React initializes an independent PGlite database.
6. The local database uses a project-specific IndexedDB identity.

Example:

- Project A: idb://joinlab-project-<project-A-UUID>
- Project B: idb://joinlab-project-<project-B-UUID>

### 6.2 Opening a Project

1. Verify the user's access to the project.
2. Check whether the local project database exists.
3. If it exists, open it.
4. Otherwise, check for a cloud snapshot.
5. If a snapshot exists, restore it.
6. Otherwise, initialize an empty PGlite database.

### 6.3 SQL Execution

- SQL executes locally through PGlite.
- Each project has an independent database.
- SQL changes persist locally through IndexedDB.
- Learner queries never execute against the Supabase application database.

## 7. Cloud Persistence

### 7.1 Snapshot Creation

1. PGlite exports the project database.
2. React sends the snapshot to the FastAPI backend.
3. FastAPI validates the access token and project ownership.
4. The snapshot is uploaded to a private Supabase Storage bucket.
5. Snapshot metadata is recorded in Supabase PostgreSQL.
6. JoinLab confirms backup success only after both operations succeed.

Snapshots are immutable and versioned.

### 7.2 Snapshot Restoration

1. Verify project ownership.
2. Retrieve the selected snapshot.
3. Download it from private Supabase Storage.
4. Restore it into the correct PGlite project database.
5. Verify successful restoration.

Restoration must not silently overwrite unsaved local changes.

### 7.3 Synchronization Strategy

The initial implementation uses explicit cloud backups and restoration.

- Local persistence is automatic through IndexedDB.
- Cloud backup is explicitly initiated by the user.
- Each cloud snapshot receives a version.
- The application tracks the last successful cloud version.
- Conflicting local and cloud versions must be detected.
- Automatic bidirectional synchronization is outside v0.3 scope.

## 8. Security Requirements

- FastAPI verifies Supabase access tokens.
- All protected endpoints require authentication.
- All application tables have RLS enabled.
- Storage bucket is private.
- Snapshot access requires project ownership.
- Supabase service-role secrets must never be exposed to the frontend.
- User-facing backend operations should preserve the authenticated user's RLS context.
- Backend environment secrets must not be committed to Git.
- API inputs and snapshot uploads must be validated.

## 9. Migration from v0.2

The existing v0.2 database is:

idb://joinlab-studio-v0.2

Migration requirements:

1. Preserve the existing v0.2 database.
2. Do not delete or reset existing data.
3. Allow the user to import the existing database into a new project.
4. Export the existing PGlite database.
5. Restore it into the new project-specific database.
6. Verify all tables, records and constraints.
7. Retain the original database until migration is successfully verified.

The migration must preserve the Employee Practice dataset and all existing user-created data.

## 10. Out of Scope for v0.3

- Team collaboration.
- Real-time collaborative editing.
- Multiple database engines.
- Automatic bidirectional synchronization.
- AI-powered SQL mentoring.
- Advanced SQL lesson authoring.

## 11. v0.3 Acceptance Criteria

The milestone is complete when:

1. Users can register, log in and log out.
2. Authenticated API access works through FastAPI.
3. Users can create multiple workspaces.
4. Users can create multiple projects in a workspace.
5. Each project has an independent PGlite database.
6. Data persists after refreshing the browser.
7. Users can create private cloud snapshots.
8. Users can restore previous snapshots.
9. Users cannot access another user's workspaces, projects or snapshots.
10. Existing v0.2 database data can be migrated without loss.
11. The React frontend works with the FastAPI backend.
12. Critical API, security and persistence workflows pass tests.
